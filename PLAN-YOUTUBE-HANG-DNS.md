> Стек VLESS + WS + TLS и сертификаты сохраняются — ничего не мигрируем.

- Уже сделано и задеплоено (коммит `8db2cf1`): в `buildSingBoxConfig` →
  `route.rules` добавлен drop QUIC (`network:'udp', port:[443]`). **Не помогло** —

- Amnezia отклонена окончательно (удалена из App Store как и все, подписки не

## 1. Главная гипотеза: сломан DNS-резолвинг

Один корень объясняет всё сразу:

- **Telegram работает** — клиент ходит по вшитым IP дата-центров, DNS почти не
  нужен.
- **YouTube и поиск виснут** — им сначала надо отрезолвить домен; если DNS через
  туннель не отвечает/душится, страница висит на «резолвинге».
- **`no such host` при обновлении профиля** — тот же самый отказ DNS, только для
  `cdn.enkeym.site`.
- **QUIC-блок не помог** — ожидаемо, QUIC тут ни при чём.

Текущая DNS-секция подписки (`src/subscription/subscription.service.ts`,
`buildSingBoxConfig`):

```
dns.servers = [
  { type:'tcp', tag:'dns-remote', server:'8.8.8.8' },   // весь DNS идёт сюда
  { type:'udp', tag:'dns-direct', server:'1.1.1.1' },   // НИГДЕ не используется
]
dns.final   = 'dns-remote'
```

Проблема: **весь DNS — это plain DNS-over-TCP на `8.8.8.8` через туннель**.
Открытый DNS (порт 53, TCP и UDP) — первое, что режут ТСПУ/операторы: он не
шифрован, легко опознаётся и дросселируется по DPI. Reality-канал при этом
пропускает мелкий трафик (Telegram), но DNS-over-TCP по нему деградирует —
ровно наблюдаемая картина. Плюс `dns-direct` объявлен, но не используется ни в
одном правиле — мёртвая запись.

## 2. Диагностика (сначала подтвердить причину, потом чинить)

Выполнять **на VPS** после рестарта сессии.

### 2.1. Убедиться, что сервер здоров

```bash
cd /home/enkeym/main/vpn-new
docker compose ps                       # контейнер up
docker compose exec vpn-bot xray version
docker compose logs --tail=100 vpn-bot | grep -iE 'xray|error|panic'
```

### 2.2. Проверить DNS изнутри контейнера (путь, которым ходит трафик клиента)

```bash
# Резолвит ли сам сервер наружу — база
docker compose exec vpn-bot nslookup youtube.com 8.8.8.8
docker compose exec vpn-bot nslookup youtube.com 1.1.1.1
```

Если наружу с сервера DNS работает (обычно да) — значит отваливается именно
**клиентский** DNS-over-TCP через туннель, а не сервер. Это подтверждает раздел 1.

### 2.3. Изолировать канал на клиенте

В приложении sing-box в группе `select` вручную выбрать `cdn-wifi` (через
Cloudflare) и открыть YouTube.

- **Заработало на cdn-wifi** → деградирует именно `reality-direct` (или DNS по
  нему). Основной фикс — раздел 3, плюс можно временно сделать `cdn-wifi`
  дефолтным (раздел 4.2).
- **Виснет и на cdn-wifi** → проблема общая (DNS), фикс раздела 3 обязателен.

## 3. Фикс №1 (основной): перевести DNS на DoH

Заменить открытый DNS-over-TCP на **DNS-over-HTTPS**: он идёт как обычный HTTPS,
неотличим от веб-трафика, его нельзя выборочно дросселировать по порту 53.

В `src/subscription/subscription.service.ts`, метод `buildSingBoxConfig`,
секция `dns`:

```typescript
      dns: {
        // DoH вместо plain DNS-over-TCP: открытый порт 53 операторы режут/душат
        // по DPI первым делом — из-за этого резолв доменов через туннель висел,
        // а Telegram (вшитые IP дата-центров) работал. DoH идёт как обычный
        // HTTPS и такой фильтрации не поддаётся.
        servers: [
          {
            type: 'https',
            tag: 'dns-remote',
            server: '1.1.1.1',
            // Bootstrap: как отрезолвить сам сервер DoH до поднятия DNS.
            // 1.1.1.1 — уже IP, но detour важен, чтобы запрос шёл в туннель.
            detour: 'select',
          },
        ],
        final: 'dns-remote',
        strategy: 'ipv4_only',
      },
```

Пояснения:

- Убрана неиспользуемая запись `dns-direct` (была мёртвой).
- `detour: 'select'` — DoH-запросы идут через выбранный пользователем канал
  (туннель), а не мимо него.
- `1.1.1.1` DoH — это IP, поэтому bootstrap-резолвинг самого DoH-сервера не нужен;
  порочного круга нет. Если Cloudflare DoH у оператора нестабилен — заменить на
  `8.8.8.8` (Google DoH) или `dns.google`.
- `default_domain_resolver: 'dns-remote'` в секции `route` **оставить как есть** —
  он уже ссылается на тег `dns-remote`, который теперь DoH.

После правки — сборка и деплой:

```bash
pnpm run build
docker compose build && docker compose up -d
```

**Важно:** это подписочный конфиг. Чтобы новый DNS применился, пользователь
должен **перетянуть профиль** в клиенте (Update/обновить подписку). Если из-за
`no such host` профиль не обновляется — см. раздел 4.1.

## 4. Если DoH не хватило

### 4.1. Клиент не может обновить профиль (`no such host`)

Пока DNS у клиента сломан, он не скачает новую подписку — замкнутый круг.
Три способа разорвать:

1. **Выключить VPN**, переключить телефон на мобильный интернет (или Wi-Fi через
   другого оператора), обновить профиль, включить обратно. Смена сети часто
   даёт рабочий системный DNS на момент скачивания.
2. На телефоне временно прописать системный DNS `1.1.1.1` / `8.8.8.8`
   (Android: приватный DNS `one.one.one.one`), обновить профиль.
3. Крайний случай — выдать подписку **по IP** сервера в обход домена (для
   разовой доставки конфига), либо переслать содержимое `/full` файлом через бот.

### 4.2. Сделать `cdn-wifi` предпочтительным каналом

Если по разделу 2.3 reality-direct деградирует, а cdn-wifi жив — переключить
дефолт группы `select` с `auto` на `cdn-wifi`, чтобы клиенты не «прилипали» к
плохому каналу:

```typescript
        {
          type: 'selector',
          tag: 'select',
          outbounds: ['auto', 'cdn-wifi', 'reality-direct'],
          default: 'cdn-wifi',   // было 'auto'
          interrupt_exist_connections: true,
        },
```

`auto` (urltest) выбирает по пингу `generate_204` — крошечный запрос проходит
даже по «полуживому» каналу, поэтому urltest считает reality-direct рабочим,
хотя объёмный трафик по нему висит. Явный дефолт `cdn-wifi` это обходит.

### 4.3. Сменить SNI/DEST Reality на менее «засвеченный»

Если reality-direct душат по маске: в `.env` на сервере
`XRAY_REALITY_SNI` / `XRAY_REALITY_DEST` заменить с популярного
`www.microsoft.com` на другой TLS 1.3-домен вне РФ (например `www.icloud.com`,
`dl.google.com`). Домен должен реально отдавать TLS 1.3. После смены —
пересобрать конфиг Reality (или пересоздать `configs/xray-reality.json`) и
перевыдать ссылки, т.к. SNI входит в `vless://`.

### 4.4. Проверить домен на DNS-poisoning РКН

`no such host` может означать, что ISP клиента отравляет DNS по домену
`enkeym.site` (Cloudflare-домены под фильтром). Проверка: на телефоне при
**выключенном** VPN сравнить `nslookup cdn.enkeym.site` на системном DNS и на
`1.1.1.1`. Если системный отдаёт мусор/пусто, а `1.1.1.1` — Cloudflare-IP,
подтверждён poisoning. Тогда DoH из раздела 3 решает проблему и в туннеле, а для
первичной загрузки профиля — способы из 4.1.

## 5. Порядок действий

1. Раздел 2.1–2.2 — подтвердить, что сервер здоров (ожидаемо да).
2. Раздел 2.3 — на клиенте вручную выбрать `cdn-wifi`, проверить YouTube.
3. Раздел 3 — внедрить DoH, собрать, задеплоить.
4. Перетянуть профиль в клиенте (при `no such host` — раздел 4.1), проверить
   YouTube и поиск.
5. Если reality-direct всё ещё плох — разделы 4.2 → 4.3.

## 6. Проверка результата

- YouTube и Google-поиск открываются через туннель без зависаний.
- Профиль в sing-box обновляется без `no such host`.
- Telegram по-прежнему работает.
- Существующие подписки Hiddify не сломаны (формат по User-Agent не менялся).

## 7. Что НЕ трогаем

- Транспорт VLESS + WS + TLS и сертификаты.
- URL `/sub/:uuid` и выбор формата base64/sing-box по User-Agent.
- Плоскую структуру группы `urltest` (в коде зафиксирован инцидент с
  зависанием вложенных групп — не разбивать).
- QUIC-drop правило из коммита `8db2cf1` — оставить, оно безвредно.
