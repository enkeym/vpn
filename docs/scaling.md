# Что применить при расширении сервера

12.08.2026 VPS расширен до **4 ядер / 7.8Gi RAM**. Пункты 1 и 3 (лимиты
контейнера и `network_mode: host`) уже применены в `docker-compose.yml` — этот
файл теперь фиксирует, что именно было сделано, и служит шаблоном на случай
следующего апгрейда. Живой чек-лист команд, которые нужно выполнить именно на
сервере (не в этом репозитории), — в разделе «Команды на сервере» в самом низу.

⚠️ **После апгрейда CPU у провайдера — перезапустить `dockerd`.** 12.08.2026
`docker info` первое время показывал `CPUs: 1`, хотя `nproc` на хосте уже
видел 4: hot-add ядер применяется на уровне гипервизора и ядра ОС сразу, но
Go-рантайм `dockerd` определяет число CPU один раз при старте процесса и не
обновляет его, пока живёт. Хост не перезагружался с 04.08 — демон стартовал
ещё на одном ядре. Фикс — `sudo systemctl restart docker` (не ребут всей
машины), после чего `docker info | grep -i cpus` показывает актуальное число.

## 1. Лимиты контейнера (обязательно после апгрейда)

`docker-compose.yml`, секция `deploy.resources.limits` — поднято с `'1.0'`/`512M`
до:

```yaml
cpus: '3.0'    # из 4 реальных — ядро оставлено хосту (ОС, sshd, conntrack, cron)
memory: 2G     # из 7.8Gi
```

При следующем апгрейде поднимать эти значения синхронно с `nproc` на хосте, но
не до предела — docker откажется стартовать контейнер, если `cpus` больше
числа реальных ядер (`Range of CPUs is from 0.01 to 1.00, as there are only N
CPUs available`), а всё до последнего ядра/гигабайта отдавать контейнеру не
стоит: сети без host-стека самого хоста тоже нужны циклы CPU.

**Почему это главный ограничитель скорости.** Туннель работает на
`amneziawg-go` — userspace-реализации: каждый пакет шифруется в Go-процессе, а не
в ядре. Сверх этого AWG 3 генерирует мусорные пакеты и добивку транспорта (S4),
то есть на байт полезных данных приходится заметно больше работы CPU, чем у
обычного WireGuard. В тот же лимит упираются NestJS-бот, sqlite и генерация
QR-кодов. На одном ядре это даёт потолок порядка сотен Мбит/с суммарно на всех
клиентов и, что заметнее, скачки задержки в момент, когда бот обрабатывает
команду.

Реального простоя при смене лимитов нет, но контейнер пересоздаётся:

```bash
docker compose up -d
```

Интерфейс `awg0` живёт внутри сетевого пространства контейнера, поэтому он
поднимется заново — соединения клиентов переустановятся за несколько секунд
(`PersistentKeepalive = 25`).

**GOMAXPROCS дополнительные ядра подхватит сам.** `amneziawg-go` собирается на
`golang:1.25-alpine` (см. `Dockerfile`), а начиная с Go 1.25 рантайм читает
cgroup-лимит CPU контейнера и сам выставляет `GOMAXPROCS` — отдельно
прокидывать переменную окружения не нужно, достаточно поднять `cpus` в
`deploy.resources.limits`. Проверить, что ядра действительно используются,
можно только по факту нагрузки (см. «Проверка после апгрейда» ниже) — рантайм
ничего не пишет в лог приложения. ⚠️ Это не отменяет фикса `dockerd` выше:
если сам демон думает, что ядро одно (не перезапускался после апгрейда), он
не даст контейнеру больше 1.0 ещё до того, как дело дойдёт до GOMAXPROCS.

**Бот от лишних ядер быстрее не станет.** NestJS-процесс (`node
dist/src/main.js`) — однопоточный, PM2/cluster не используется. Дополнительные
ядра дают то, что `amneziawg-go` и бот перестают драться за одно ядро, но сам
бот как был event-loop на одном потоке, так и остался. Если после апгрейда
узкое место окажется именно в боте (а не в шифровании трафика), смотреть в
первую очередь на синхронные CPU-тяжёлые места — генерацию QR
(`peers.service.ts`, `qrcode`) и ключей (`tunnel.utils.ts`) — и выносить их в
`worker_threads`, а не пытаться решить лимитами контейнера.

## 2. UDP-буферы ядра хоста (не зависит от числа ядер, но проверить стоит)

Не namespaced, из контейнера не задаётся. `wireguard-go` запрашивает ~7 МБ на
сокет, при дефолтных ~208 КБ пакеты теряются на бурстах. Начиная с перехода на
`network_mode: host` это ставится тем же файлом, что и forwarding — см.
`/etc/sysctl.d/99-vpn.conf` в разделе «Команды на сервере» ниже, отдельно
делать не нужно.

## 3. `network_mode: host` (применено 12.08.2026)

Раньше каждый пакет проходил двойной NAT: MASQUERADE внутри контейнера плюс
DNAT docker снаружи (секция `ports`), и оба раза через conntrack. На одном
ядре выигрыш от устранения этого съедался, на нескольких — заметен, поэтому
сделано вместе с апгрейдом.

`docker-compose.yml`: `ports` убраны, добавлено `network_mode: host` на
уровне сервиса. Из этого следует три момента, которые раньше делал docker
автоматически, а теперь их нужно один раз настроить на самом хосте:

1. **`sysctls` в compose (`net.ipv4.ip_forward`, `net.ipv6.conf.all.*`) в
   host-режиме docker к контейнеру не применяет** — их нужно выставить прямо
   на хосте (см. «Команды на сервере», sysctl-блок).
2. **Проброса `AWG_PUBLIC_PORT` (4500) → `AWG_PORT` (51821) через docker больше
   нет.** Контейнер в host-режиме сразу слушает `AWG_PORT` на хосте, а публичный
   4500/udp (порт IPsec NAT-T — его пропускают мобильные операторы, которые
   режут нестандартные UDP-порты, см. заметку про мобильного оператора в памяти
   проекта) нужно перенаправлять на 51821 вручную через `iptables REDIRECT`.
   Менять сам `AWG_PORT` на 4500 нельзя — он записан в `awg0.conf`, смена
   пересоздаёт конфиг и отключает всех уже выданных клиентов.
3. **Оба порта (4500 и 51821) нужно открыть во входящем фаерволе хоста** —
   раньше это делал docker при публикации портов, в host-режиме открывать
   вручную.

**Увеличение числа клиентов.** Подсеть `/16` (`AWG_ADDRESS=10.9.0.1/16`) даёт
65 533 адреса — не ограничение. Ограничение — CPU из пункта 1.

## Команды на сервере

Выполняются на самом VPS (не в этом репозитории), один раз после `git pull` +
до `docker compose up -d --build`. Порядок важен: сначала фикс `dockerd` и
sysctl/фаервол, потом пересоздание контейнера — иначе между поднятием
`network_mode: host` и настройкой iptables туннель на секунды-минуты
останется без форвардинга и без проброса 4500.

```bash
# 0. если сервер не перезагружался с момента апгрейда CPU у провайдера —
#    dockerd мог закэшировать старое число ядер, см. врезку в начале документа
docker info | grep -i cpus
#    если меньше, чем nproc — перезапустить демон (не весь сервер):
sudo systemctl restart docker

# 1. forwarding + UDP-буферы ядра — раньше половину задавал docker sysctls,
#    в network_mode: host он этого не делает, выставляем сами одним файлом
cat <<'EOF' | sudo tee /etc/sysctl.d/99-vpn.conf
net.ipv4.ip_forward=1
net.ipv6.conf.all.disable_ipv6=0
net.ipv6.conf.all.forwarding=1
net.core.rmem_max=26214400
net.core.wmem_max=26214400
EOF
sudo sysctl --system

# 2. открыть публичный и внутренний порт туннеля во входящем фаерволе
#    (ufw — если он используется; иначе см. iptables-вариант ниже)
sudo ufw allow 4500/udp
sudo ufw allow 51821/udp
# --- или, если ufw не используется ---
sudo iptables -A INPUT -p udp --dport 4500 -j ACCEPT
sudo iptables -A INPUT -p udp --dport 51821 -j ACCEPT

# 3. проброс 4500 -> 51821 (раньше делал docker DNAT, теперь host-режим не даёт)
sudo iptables -t nat -A PREROUTING -p udp --dport 4500 -j REDIRECT --to-port 51821

# 4. сохранить iptables-правила, чтобы они пережили перезагрузку хоста
sudo apt-get install -y iptables-persistent   # спросит сохранить текущие правила — да
sudo netfilter-persistent save

# 5. пересоздать контейнер с новым compose (network_mode: host, cpus 3.0/2G)
docker compose up -d --build
```

## Проверка после апгрейда

```bash
nproc                                       # сколько ядер стало
docker stats --no-stream vpn-tgbot          # упирается ли контейнер в лимит CPU
docker compose logs --tail=50 vpn-tgbot | grep -iE 'amneziawg|ipv6'
docker exec vpn-tgbot top -bn1 | head -15   # кто именно ест CPU: node или amneziawg-go
sudo ss -lunp | grep -E ':4500|:51821'      # слушает ли awg0 порт на самом хосте (не docker port — в host-режиме он ничего не покажет)
sudo iptables -t nat -L PREROUTING -n --line-numbers | grep 4500   # проброс 4500→51821 на месте
```
