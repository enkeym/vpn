# CDN XHTTP через Cloudflare Tunnel

Канал `CDN XHTTP` использует VLESS, TLS до Cloudflare с fingerprint Chrome
и ALPN h2, транспорт XHTTP `packet-up`. Загрузка идёт отдельными POST
по 16–64 КиБ со случайным интервалом 10–30 мс; XHTTP добавляет случайную
набивку 100–1000 байт. Повторное использование HTTP/2-соединений ограничено
случайными диапазонами Xray. Origin не попадает в подписку.

Это альтернативный транспорт для случая, когда WebSocket устанавливается,
но передача зависает. Размер POST не является MTU. Скачивание остаётся потоком:
ограничение каждого TLS-соединения по объёму эти настройки не устраняют.
Обход блокировок по домену, IP Cloudflare или поведенческому анализу не гарантирован.

## Включение

1. Выбрать hostname существующего Cloudflare Tunnel. Можно использовать тот же
   hostname, что у WebSocket, с отдельным маршрутом по пути.
2. Сгенерировать постоянный случайный путь: `openssl rand -hex 16`.
   Указать в окружении приложения:

   ```dotenv
   XRAY_CDN_XHTTP_HOST=cdn.example.com
   XRAY_CDN_XHTTP_PORT=8003
   XRAY_CDN_XHTTP_PATH=/<результат команды>/
   ```

   В реальном значении нужны начальный и конечный `/` и не менее 16 символов
   между ними. Приложение проверяет домен, порт и путь при создании сервиса.
   Пустой `XRAY_CDN_XHTTP_HOST` отключает канал. Порт слушает только 127.0.0.1.

3. В конфигурации cloudflared добавить правило **раньше** существующего правила
   для всего hostname. Пример фрагмента `ingress`, где вместо `RANDOM_PATH`
   используется тот же результат команды:

   ```yaml
   ingress:
     - hostname: cdn.example.com
       path: ^/RANDOM_PATH/.*$
       service: http://127.0.0.1:8003
       originRequest:
         httpHostHeader: cdn.example.com
         disableChunkedEncoding: false
     - hostname: cdn.example.com
       service: http://127.0.0.1:8002
     - service: http_status:404
   ```

   Для remotely managed Tunnel настроить такой же маршрут в Cloudflare.
   Пример не заменяет остальные существующие ingress-правила. Cloudflared
   должен видеть loopback хоста, где работает Xray; внутри отдельного контейнера
   его собственный 127.0.0.1 не подходит. HTTP/2 до origin включать не требуется.

4. Для этого пути отключить кэширование и интерактивные проверки Cloudflare,
   если они включены. POST и GET должны доходить без перенаправлений и challenge.
   Не отключать защиту остальных маршрутов. При промежуточном nginx отключить
   `proxy_buffering` и `proxy_request_buffering`, разрешить долгий ответ GET.
5. Применить конфигурацию Tunnel и приложение, затем обновить подписку клиента.
   XHTTP появляется первым в base64 и Xray JSON; WS сохраняется вторым.
   Применение конфигурации к действующему серверу выполняется отдельно.

## Клиенты и проверка

Нужно ядро Xray с XHTTP, совместимое с серверным `v26.3.27`, закреплённым
в Dockerfile. Предпочтителен JSON-формат подписки `?format=xray`: некоторые
импортёры VLESS-ссылок отбрасывают `extra` и теряют параметры дробления.
В штатном sing-box JSON остаётся WebSocket: неподдерживаемый XHTTP туда
не добавляется. Для таких клиентов нужен Xray-совместимый клиент.

Проверять отдельно загрузку и скачивание файла хотя бы 1 МиБ из московской сети,
а также повторное подключение после отзыва UUID. Успешный TLS handshake или GET
к корню домена не подтверждает работу туннеля. Ошибки 502/504 указывают на
маршрут/origin. Не публиковать реальные UUID, пути, ключи и токены в логах.

Параметры транспорта: [документация разработчиков Xray](https://github.com/XTLS/Xray-core/discussions/4113).
